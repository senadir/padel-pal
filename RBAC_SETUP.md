# RBAC Setup Guide

This guide explains how to complete the setup of Role-Based Access Control (RBAC) for Padel Pal, following the official Supabase tutorial.

## Overview

The RBAC system uses Supabase's custom JWT claims feature to add role information to user authentication tokens. This follows the official pattern from the [Supabase RBAC documentation](https://supabase.com/docs/guides/database/postgres/custom-claims-and-role-based-access-control-rbac).

## Architecture

Unlike storing roles directly on the `players` table, this implementation follows the Supabase recommended pattern with a separate `user_roles` table and an enum type:

- **`app_role` enum**: Defines valid roles (`'player'`, `'organizer'`)
- **`user_roles` table**: Maps users to roles (users can have multiple roles)
- **JWT hook function**: Adds the user's highest privilege role to JWT tokens
- **RLS policies**: Check the `user_role` claim from JWT tokens

## What You Need to Do

### Register the JWT Hook in Supabase Dashboard

The JWT hook function exists in the database but needs to be registered with Supabase Auth. This is a **manual step** that must be done in the Supabase Dashboard.

#### Steps:

1. **Open Supabase Dashboard**
   - Go to https://supabase.com/dashboard
   - Select your project

2. **Navigate to Authentication Hooks**
   - In the left sidebar, click **Authentication**
   - Click on the **Hooks** tab (may be labeled as "Beta")

3. **Enable Custom Access Token Hook**
   - Find the **"Custom Access Token"** section
   - Click **"Enable Hook"** or **"Add a new hook"**

4. **Configure the Hook**
   - **Hook Type**: Custom Access Token
   - **Schema**: `public`
   - **Function**: `custom_access_token_hook`
   - Full reference: `public.custom_access_token_hook(event jsonb)`

5. **Save and Enable**
   - Click **"Create"** or **"Save"**
   - Ensure the hook is enabled (toggle should be ON)
   - The hook will now run automatically during authentication and token refresh

### Verify the Hook is Working

## How It Works

### 1. Database Schema

```sql
-- Enum defines valid roles
CREATE TYPE public.app_role AS ENUM ('player', 'organizer');

-- Table maps users to roles (many-to-many)
CREATE TABLE public.user_roles (
  id BIGINT GENERATED BY DEFAULT AS IDENTITY PRIMARY KEY,
  user_id UUID REFERENCES auth.users ON DELETE CASCADE NOT NULL,
  role app_role NOT NULL,
  created_at TIMESTAMPTZ DEFAULT NOW(),
  UNIQUE (user_id, role)
);
```

### 2. JWT Hook Function

```sql
CREATE OR REPLACE FUNCTION public.custom_access_token_hook(event JSONB)
RETURNS JSONB
LANGUAGE plpgsql
STABLE
AS $$
DECLARE
  claims JSONB;
  user_role public.app_role;
BEGIN
  -- Fetch the user's highest privilege role
  -- (organizer > player alphabetically, so ORDER BY works)
  SELECT role INTO user_role
  FROM public.user_roles
  WHERE user_id = (event->>'user_id')::UUID
  ORDER BY
    CASE role
      WHEN 'organizer' THEN 1
      WHEN 'player' THEN 2
    END
  LIMIT 1;

  claims := event->'claims';

  -- Set user_role claim (default to 'player' if no role found)
  IF user_role IS NOT NULL THEN
    claims := jsonb_set(claims, '{user_role}', to_jsonb(user_role));
  ELSE
    claims := jsonb_set(claims, '{user_role}', to_jsonb('player'::public.app_role));
  END IF;

  event := jsonb_set(event, '{claims}', claims);
  RETURN event;
END;
$$;

GRANT EXECUTE ON FUNCTION public.custom_access_token_hook TO supabase_auth_admin;
```

### 3. RLS Policies

Example from the `sessions` table:

```sql
-- Only organizers can insert sessions
CREATE POLICY "sessions_organizer_insert" ON sessions
  FOR INSERT
  TO authenticated
  WITH CHECK ((auth.jwt() ->> 'user_role')::public.app_role = 'organizer');
```

The key part: `(auth.jwt() ->> 'user_role')::public.app_role = 'organizer'`
- `auth.jwt()` returns the JWT token as JSONB
- `->> 'user_role'` extracts the user_role claim as text
- `::public.app_role` casts it to the enum type
- `= 'organizer'` checks if it matches

### 4. Application Integration

```typescript
// In auth.ts
export const fetchUser = createServerFn({ method: 'GET' }).handler(async () => {
  const supabase = getSupabaseServerClient()
  const { data } = await supabase.auth.getUser()

  // ... player fetching logic ...

  // Fetch user's role from user_roles table
  const { data: userRoles } = await supabase
    .from('user_roles')
    .select('role')
    .eq('user_id', data.user.id)

  const role = userRoles?.find((r) => r.role === 'organizer')?.role
    || userRoles?.[0]?.role
    || 'player'

  return { user, player, isPhoneVerified, hasPlaytomicProfile, role }
})

// In components
import { useRole, useIsOrganizer } from '@/contexts/auth'

function MyComponent() {
  const role = useRole() // 'player' | 'organizer'
  const isOrganizer = useIsOrganizer() // boolean
}
```

## Role Permissions

### Player Role (default)
- View all sessions and matches
- Vote on session time slots
- Join/leave matches
- Manage own profile
- Delete own votes

### Organizer Role (all player permissions plus)
- Create/edit/delete sessions
- Create/edit/delete matches
- Add/remove any player from matches
- Delete any votes
- Manage games (legacy)
- Manage user roles (via `user_roles` table policies)

## Adding New Users as Organizers

To grant organizer role to a user:

```sql
-- Add organizer role (keeping player role too)
INSERT INTO public.user_roles (user_id, role) VALUES
  ('USER_UUID_HERE', 'organizer')
ON CONFLICT (user_id, role) DO NOTHING;
```

The user will receive the new role in their JWT on the next token refresh (or sign-out/sign-in).

## Troubleshooting

### Hook not appearing in dashboard
- Ensure you're looking at the correct project
- Check that the function exists:
  ```sql
  SELECT proname, prosrc FROM pg_proc WHERE proname = 'custom_access_token_hook';
  ```
- Verify function permissions:
  ```sql
  SELECT grantee, privilege_type
  FROM information_schema.routine_privileges
  WHERE routine_name = 'custom_access_token_hook';
  ```

### Role not appearing in JWT
- Ensure the hook is **enabled** in the dashboard (not just created)
- Sign out and sign back in to get a fresh token
- Check that user has a role assigned:
  ```sql
  SELECT * FROM public.user_roles WHERE user_id = auth.uid();
  ```
- Inspect the JWT token at https://jwt.io - look for `user_role` claim

### Permission denied errors
- Verify the user's role:
  ```sql
  SELECT role FROM public.user_roles WHERE user_id = auth.uid();
  ```
- Check RLS policies:
  ```sql
  SELECT tablename, policyname, cmd, qual, with_check
  FROM pg_policies
  WHERE schemaname = 'public' AND tablename = 'sessions';
  ```
- Ensure JWT includes role claim (see above)
- Try the operation in SQL to see the exact error:
  ```sql
  -- As the authenticated user
  INSERT INTO sessions (...) VALUES (...);
  ```

### "User not found in user_roles" errors
- New users need to be added to `user_roles` table
- By default, users should get the `'player'` role
- The hook defaults to `'player'` if no role found
- Consider creating a trigger to auto-assign `'player'` role on user creation:
  ```sql
  CREATE OR REPLACE FUNCTION public.handle_new_user()
  RETURNS TRIGGER AS $$
  BEGIN
    INSERT INTO public.user_roles (user_id, role)
    VALUES (NEW.id, 'player')
    ON CONFLICT (user_id, role) DO NOTHING;
    RETURN NEW;
  END;
  $$ LANGUAGE plpgsql SECURITY DEFINER;

  CREATE TRIGGER on_auth_user_created
    AFTER INSERT ON auth.users
    FOR EACH ROW EXECUTE FUNCTION public.handle_new_user();
  ```
